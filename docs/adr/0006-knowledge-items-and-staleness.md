# ADR 0006: Knowledge items, staleness, and project grounding

**Status:** accepted

**Context.**
In v0.1-v0.3, skills (e.g. `python.testing`, `databases.sqlite`) were the primary unit of learning.
However, developers building projects with AI coding agents struggle not with abstract language skills,
but with explaining their *own project*: what specific files do, why architectural decisions were made,
and what changed when the AI updated code later. Language skills remain useful tags, but knowledge items
(components, decisions, concepts, and bug-fixes anchored to real project files) replace skills as the
primary learning unit.

**Decisions.**
1. **Knowledge Items as Central Unit:**
   - The primary learning artifact is a project-grounded knowledge item (`knowledge_items`), categorized
     into bands (Basic, Intermediate, Advanced) and kinds (`component`, `decision`, `concept`, `bug-fix`).
   - Every knowledge item must reference between 1 and 12 files that exist in the union of ingested commits.
   - Learner mastery is tracked via verbatim explain-backs (`explanations`), organized by target audience
     and depth ladder (1 what, 2 how, 3 why, 4 trade-offs, 5 scale/failure).

2. **Derived Staleness:**
   - An item is STALE when it has been explained or marked shaky, and a newer ingested git commit
     touches any of the item's files strictly after its `baseline_committed_at`.
   - Staleness is a derived query, never a destructive status change.
   - Returning stale items includes up to 5 changing commits and the baseline sha so agents can compute diffs.

3. **Staleness Limitations & Boundary Rules:**
   - **Timestamp tie rule**: The staleness check requires `committed_at > baseline_committed_at` (strictly greater).
     Because git commit timestamps typically have 1-second resolution, commits created in the exact same second
     as the baseline commit are not detected as newer.
   - **Uncommitted edits are invisible**: Staleness only monitors ingested git commits. Local working-tree
     modifications and unstaged edits are not visible to the server until committed.
   - **Authorship boundary**: The server cannot verify whether `learner_text` was written by the human learner
     or generated by the AI agent. The audit trail stores verbatim text to ensure accountability and reviewability.

4. **Pull-Based Spaced Repetition**:
   - The server does not run background push notifications or daemons. Review schedules are evaluated
     on-demand during IDE session starts via pull-based briefing and review queries.
